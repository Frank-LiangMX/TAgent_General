## 0. TL;DR

当前最需要解决的不是 Ask 是否继续保留，而是 Agent 会话里的 `btw` 语义和底层都不对齐。

现在确认的新方向是：

1. `btw` 的核心价值不是“长期分支”，而是“**不中断主任务的即时解释通道**”
2. `btw` 默认是 **一次性的、临时的、依附当前 Agent 现场的 side thread**
3. `btw` 底层仍然应该复用 Agent runtime / fork 能力，这样才能自然支持 `kscc`
4. Ask 仍然应该从 Agent 会话内部模式中拆出去，回到独立会话类型

一句话概括：

`BTW = 运行中 Agent 任务的临时伴随问答面板，不承担长期会话分支职责。`

---

## 1. 背景与真实问题

### 1.1 当前 `btw` 的根问题

当前 `btw` 实现在 `apps/electron/src/main/lib/btw-service.ts`，历史上是轻量 provider/SSE 方案。它的问题不是 UI，而是底层定位错误：

- 它不属于 Agent runtime
- 它天然丢失 `kscc-internal` 一类非直连 provider/SSE 渠道能力
- 它为了“共享上下文”只能自己拼历史摘要

所以它更像一个特例聊天请求，而不是 Agent 会话原生的一部分。

### 1.2 当前 Ask 的根问题

Ask 现在被放进 Agent 会话里，当成 composer mode 使用，但底层又和 Agent 分裂：

- UI 上像是在同一会话里切 Ask / Agent
- 底层却是 Ask 和 Agent 两套运行时、两套存储
- 用户直觉以为上下文互通，实际并不完全成立

这使 Ask 和 BTW 两个概念被错误绑在了一起。

### 1.3 用户真实需求不是“再开一个正式分叉”

用户刚刚确认的真实使用场景是：

- 主 Agent 任务正在进行
- 不想打断它
- 但对它刚才做的事不理解，想马上问一句

这说明 BTW 的重点不是“保留历史”或“长期演化”，而是：

- 不打断主任务
- 快速解释当前现场
- 只服务这一刻的理解需求

所以 BTW 更适合被定义为：

**运行中主任务的临时伴随解释通道**

而不是：

**从主会话长期分叉出来的第二条正式会话线**

---

## 2. 目标

### 2.1 目标

- `btw` 必须支持 `kscc`
- `btw` 必须复用 Agent runtime，而不是继续维护 provider/SSE 特例链路
- `btw` 在主任务运行中必须可用，但默认不打断主任务
- `btw` 必须被定义为一次性、临时 side thread，而不是长期正式分支
- Ask 必须从 Agent 会话内部模式中拆出，恢复为独立会话类型
- `BTW / Fork / Ask` 三者边界必须明确

### 2.2 非目标

- 本次不把 Ask 也完全迁入 Claude Code SDK
- 本次不让 BTW 自动持续同步主会话后续新增上下文
- 本次不把 BTW 设计成长期保留历史的正式分支系统
- 本次不优先解决 Ask 的全部渠道对齐问题

---

## 3. 核心定义

### 3.1 BTW

`BTW` 定义为：

- Agent 会话内部的临时 side thread
- 服务“当前现场解释”
- 默认一次性
- 默认不进入正式历史列表
- 默认不承担长期演化职责

它可以基于 fork/runtime 实现，但产品语义上不等于“正式 fork 会话”。

### 3.2 Fork

`Fork` 定义为：

- 从某个主会话节点显式分支
- 后续独立演化
- 可以保留历史
- 可以作为正式会话继续存在

### 3.3 Ask

`Ask` 定义为：

- 独立的轻量对话会话
- 不依附某个正在执行的 Agent 现场
- 不承担 BTW 的伴随解释职责

---

## 4. 关键语义规则

### 4.1 主会话空闲时

当主会话当前没有活跃任务时：

- 可以发起 BTW
- BTW 仍然是临时 side thread
- 它拿的是发起时刻的主会话快照
- 默认问完即弃

### 4.2 主会话运行中时

当主会话当前有活跃任务时：

- 允许发起 BTW
- 默认不打断主任务
- BTW 回答基于“当前可用快照”理解现场
- 它**不承诺持续继承后续主会话新增上下文**
- 它的核心职责是解释，不是并行长期演化

这一条是本次设计最重要的原则。

### 4.3 BTW 不自动保留为正式历史

默认情况下：

- BTW 不应该长期留在主会话历史结构里
- 它可以有运行时状态和临时消息状态
- 但不默认成为一个正式常驻 fork 会话

### 4.4 需要长期继续时显式升级

如果用户在 BTW 里聊深了，想继续：

- 应通过显式动作“转为正式分支”
- 升级后它才成为真正 `Fork`
- 升级前它都只是临时解释通道

---

## 5. 三者边界

| 能力 | Ask | BTW | Fork |
|---|---|---|---|
| 所属层级 | 独立会话类型 | Agent 会话内临时 side thread | 正式分支会话 |
| 主要用途 | 普通轻量对话 | 运行中任务即时解释 | 长期独立继续 |
| 是否依附当前 Agent 现场 | 否 | 是 | 来自某个节点，但之后独立 |
| 是否默认支持 `kscc` | 后续补齐 | 是，复用 Agent runtime | 是，复用 Agent runtime |
| 是否默认保留历史 | 是 | 否 | 是 |
| 是否持续继承主会话后续发展 | 否 | 否 | 否 |
| 是否可升级为正式分支 | 不适用 | 是 | 已经是 |

结论：

**BTW 不是迷你 Ask，也不是默认常驻 Fork。它是 Agent 现场里的临时解释层。**

---

## 6. 运行时方案

### 6.1 为什么底层仍然用 fork/runtime

虽然产品语义上 BTW 是临时的，但底层仍然推荐复用 fork/runtime，因为这样可以：

- 自然继承 `kscc`
- 继承 Claude Code SDK / 权限 / 渠道能力
- 避免重新维护一套 provider/SSE 特例
- 让 BTW 与正式 Agent 通道保持一致的能力来源

### 6.2 运行时实现约束

建议的 BTW 运行时约束：

1. 发起 BTW 时，从当前 Agent 会话创建一次临时 side thread
2. side thread 生命周期绑定 BTW 面板
3. 关闭 BTW、主会话切换、或主任务结束后，可自动失效或回收
4. 默认不出现在正式会话列表
5. 默认隐藏工具噪音，只展示简洁回答和必要状态

### 6.3 主任务运行中时的行为

主任务运行中发起 BTW 时：

- 不 stop 主任务
- 不 interrupt 当前任务
- BTW 只消费发起时的快照和当前可见上下文
- 明确接受“解释基于当前快照，非实时同步”的语义

---

## 7. UI 规则

### 7.1 BTW 面板

BTW 面板应保持轻量：

- 入口不变
- 面板结构不必大改
- 回答尽量简洁
- 默认不显示工具调用、复杂中间过程、推理噪音
- 更像“解释浮层”而不是“第二主会话”

### 7.2 升级路径

BTW 面板只需要保留一个明确升级动作：

- `转为正式分支`

不需要默认暴露过多线程管理能力。

### 7.3 Ask 入口

Ask 不再作为 Agent 会话内档位出现，而是：

- 回到独立入口
- 独立列表
- 独立存储

---

## 8. 实施步骤

### 8.1 Phase 1: 语义定稿

- 明确 BTW 是临时解释通道
- 明确 BTW 不等于长期 fork
- 明确 Ask / BTW / Fork 三者边界
- 通过 ADR 固化方向

### 8.2 Phase 2: BTW 底层稳定化

- BTW 底层继续复用 Agent runtime
- 增加临时 side thread 元数据
- 增加生命周期回收和隐藏策略
- 增加主会话 active 时的行为约束

### 8.3 Phase 3: Ask 拆出

- 移除 Agent 会话内 Ask/Agent composer mode 心智
- Ask 改回独立会话类型
- 保留从 Ask 升级为 Agent 的入口，但不在原地切换

---

## 9. 验收标准

### 9.1 BTW

- 主任务运行中可发起 BTW
- 发起 BTW 不会打断主任务
- BTW 可在 `kscc-internal` 渠道下正常工作
- BTW 默认仅展示简洁解释性回答
- BTW 默认不作为正式常驻历史保留
- 需要长期继续时可显式升级为正式分支

### 9.2 Ask

- Ask 不再被当成 Agent 会话内部档位的最终方向
- Ask 产品定位恢复为独立轻量对话

### 9.3 文档

- ADR 明确写清 BTW 新语义
- 历史 ADR 与新 ADR 的替代关系清晰
